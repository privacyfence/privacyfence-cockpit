Manual checks for PrivacyFence Cockpit v1

What only you can do, before and after /implement builds the cockpit. Tick each step as you go; the ticks stay in this browser. Never paste a token, the master key, a deploy key or a password into chat or the pull request.

Before implementation

Nothing. Every phase builds against a fake privacyfence-sync and in-process test servers, so you can run /implement straight away.

After implementation

Do these once the feature PR is merged and the first release has been cut (Actions → Release, dry_run off). Item 3 also needs a privacyfence-sync release that has run --result-file and permissions.

1. Make the image public

ma1-ghcr-publicabout 5 min

A new GHCR package of a private repository starts private, so nobody else can pull it. Only an organization owner can change that.

Report back in the PRma1: package public, anonymous pull OK on <arch>

2. Get a scoped token for a test recipe

ma2-scoped-tokenabout 15 min

The cockpit accepts only PrivacyFence scoped tokens (pfst_…). Pick one harmless recipe in your recipe repository as the test recipe, for example a read-only import.

Report back in the PRma2: scoped tokens enabled, token "cockpit-test" created (90 days)

3. Run the released image on a real host

ma3-real-host-runabout 60 min

CI proves the image starts and checks a fixture. Only a real host shows the deploy key, the token check, preflight, a scheduled run and a webhook against the real PrivacyFence and GitHub.

The recipe repository's requirements.txt must pin a privacyfence-sync release that has run --result-file and permissions. If the dashboard shows "privacyfence-sync in requirements.txt is too old for the cockpit", that release is not out yet: stop here and report it.
Report back in the PRma3: setup OK, deploy key OK, token OK (<days> days), preflight OK, scheduled run <outcome>, denied webhook received: yes/no
